# Troubleshooting and Logging

意図しない問題やエラーが発生した際のデバッグ、原因究明、およびログ拡充についての必須プロセスです。

## 手順

0. **CodeGraph によるコード構造・影響範囲分析 (CodeGraph First)**
   - 不具合やエラー箇所の調査・修正を行う際、広範囲な grep や推測によるファイル全体の連続読み込みを行ってはならない。
   - 必ず CodeGraph（MCPツール codegraph_explore、または CLI codegraph explore <symbol> / codegraph impact <symbol> / codegraph callers <symbol>）をファーストコールし、対象シンボル・呼出元・呼出先・影響範囲（Blast Radius）を一撃で把握すること。

1. **証拠起点調査原則 (Evidence-First Investigation) ＆ 保存ファイル最優先利用**
   - パースエラー、0件取得異常、アクセス遮断、タイムアウト等の調査を行う際、**必ず最初に logs/runs/<日付>/error_pages/ またはストレージ上に退避された生HTMLファイルおよびメタデータJSONをロードして検証することを絶対義務**とする。
   - 現場の生HTMLを確認せず、推測のみで修正したり、保存ファイルがあるにもかかわらず無駄に外部サイトへライブ再リクエストを連打する行為を禁止する。

2. **問題調査の鉄則：仮説反証の徹底 ＆ 証跡先行原則 (Mandatory Falsification & Observability Before Conclusion)**
   - **すべての仮説は必ず反証（Falsification）を試みること**:
     - 原因に対する仮説を立てた際、都合の良い事例だけで「原因特定」と結論づけてはならない。
     - 必ず「もしその仮説が正しいなら、なぜ同条件の別ジョブ・別ケースでは成功したのか？」「タイムスタンプやカウンタの数値と矛盾しないか？」という反証テストを実施し、反証を生き残った事実のみを確定原因として扱うこと。
   - **決定的な結論に至るための情報が取得できていない時は、結論を急がず情報取得の手段（ログ・テレメトリ）を先に整えること**:
     - 「どのURLで」「どの処理（フェーズ・関数・スタックトレース）で」「その時点のハードウェアリソース（CPU・メモリ）・ネットワーク接続・DBコネクションがどうなっていたか」の決定的な証跡が欠けている状態で、推測で原因を断定することを厳禁とする。
     - 証跡が不足している場合は、まず確実にログ・診断スナップショット・New Relicメトリクスを取得・永続化する仕組みを実装・配備することを最優先とすること。

3. **事実の収集とログ・テレメトリ拡充（関心事の分離・スレッド安全性）**
   - 問題の特定には事実の収集が重要であるため、ログおよびテレメトリ（New Relic等）に出力する情報は十分かつ詳細なものにすること。
   - 死活監視（Heartbeat touch）と状態診断ダンプ（Diagnostics）の責務を混ぜてはならない（Single Responsibility Principle）。
   - マルチスレッド環境で状態記録を行う際は、ファイル競合やロック待ちを防ぐためスレッド間で同一ファイルを共有書き込みせず、スレッドローカルまたはスレッドID別ファイルに分離すること。

4. **一時ファイルの管理 (Tempフォルダ制約)**
   - デバッグスクリプト、再現用HTML、DOM確認ツールなど、一時的に使用する作業用のコードや出力ファイルは、必ず `Temp` フォルダに作成・保存すること。
   - 作業終了後は `Temp` フォルダ内に留めるか、不要であれば削除してプロジェクト直下を汚さないようにする。

5. **ルールと問題解決の自己反映**
   - 繰り返しユーザーから同じ指摘を受けた場合、それは重要な指示であると判断し、プロジェクトのルール（または関連するワークフロードキュメント）として記録・保存すること。
   - 起こした問題の解決方法（再発防止策）についても、都度関連ドキュメントに追記・反映させること。

# プロジェクト共通開発ルール

## サブエージェント・メインエージェントのモデル利用方針
- 簡単な作業（ブラウザでの単純な巡回、情報の収集、UI動作確認など）は、コスト効率の高い（安い）AIモデル（Gemini 3.5 Flash 等）のサブエージェントを利用して処理させる。
- 高コストなモデル（Claude Opus 等）は使用せず、常にコスト効率の高いモデル（Gemini 3.5 Flash等）を利用することを遵守する。
- 開発者（AIエージェント）自身も作業を行う際は常にこの方針を念頭に置き、ユーザーからのすべての指示でコスト効率の高いモデルの使用を徹底する。

## 1物件1AIリクエスト原則（Single Unified LLM Request Per Property）
- クローリング中、データパース時、またはML評価バッチ実行中において、同一物件に対してAI（Gemini等）を小分けに複数回呼び出すこと（種別判定で1回、設備で1回、画像で1回など）を厳禁とする。
- 物件に対してAIを利用する場合は、タイトル、スペック、特徴タグ、アピール文、スニペット等の全情報を1つのプロンプトに集約し、**必ず「1物件につき1リクエスト」で必要な全観点（種別判定、建物マスタ属性、専有部スペック、土地固有スペック、権利関係、画像評価等）を一括して構造化JSONで抽出・判定**させること。
- ルールベース（正規表現・セレクター）で高速に確定できる項目は極力そちらで処理し、AI呼び出しが必要な物件のみ1リクエスト完結で処理してコストとレイテンシを最小化する。

## 物件種別別 Base パーサー階層アーキテクチャ原則
- `src/crawler/package/parser/` 配下に定義されるすべてのパーサークラスは、`ParserBase` 直下に新設された物件種別ごとの Base パーサークラス（`MansionParserBase`, `KodateParserBase`, `TochiParserBase`, `InvestmentParserBase` 等）を必ず継承しなければならない。
- `ParserBase` には全種別共通項目、種別 Base には種別特有項目の抽象メソッド (`@abstractmethod`) を定義し、全パーサーが漏れなく実装しているかを単体テスト (`test_parser_abstract_methods.py`) により客観的に全件検証・継続監視する。

- コード修正を提案する際は、ファイル全体を再出力するような高コストな書き換えは避け、最小限の変更ブロック（Micro-Diffまたは特定箇所のReplace）に絞ってコード生成を行う。
- 未使用のライブラリや不要なデッドコードは、コンテキスト肥大化を防ぐために積極的に自動削除（`ruff check --fix` 等によるクリーンアップ）を行う。

## Slack通知の疎通自己チェックルール
- Slackの通知先チャンネル名（スペルなど）の変更、あるいはBotがチャンネルに招待されていないことが原因で通知が不達（`channel_not_found` 等）になる問題を防ぐため、クローリングおよび価格推定パイプラインの起動前（Step 0）に必ずSlackの疎通自己チェック（`src/crawler/scripts/debug_tools/check_slack_connection.py`）を実行して検証すること。


## コンテナ変更時の事実検証ルール
- Dockerfile、docker-compose、devcontainerなどのコンテナ構成定義や依存関係を変更した際は、単にビルド成功ログを確認するだけではなく、コンテナが実際に新規ビルド・再作成された事実を裏付けすること。
- また、変更内容（追加したコマンドの存在やマウントされたディレクトリなど）が、実際に起動しているコンテナ内に正しく反映されているかを、事前にコマンド実行（例: `docker-compose exec -T app command -v ps` 等）で自己検証すること。
- 上記による事実の裏付けが取れるまでは、推測のみでユーザーに環境の切り替えや動作確認を求めてはならない。

## パス指定の原則（ホスト・コンテナ間依存の排除）
- ログや一時ファイルなどの保存先パスを記述する際は、`/app/` などの特定の絶対パスをハードコードしてはならない。
- 常に `__file__` などから動的にプロジェクトのルートディレクトリを算出し、`os.path.join` で相対的に組み立てること。これによりホスト側（Windows等のホストOS）とコンテナ側（Docker）の両方の実行環境で正しくパスが動作することを保証すること。

## Pythonインポートの配置原則（冒頭インポート統一）
- `import` 文を関数内やコードの中盤・後方に記述してはならない。必要なすべてのモジュールインポート（標準ライブラリ、サードパーティ、プロジェクト内モジュール）は、必ずファイルの最上部（冒頭）に集約・完結させること。
- 設定初期化が必要なスクリプトでは、ファイルの冒頭で `import setup_env` を呼び出し、共通の環境・パスロードを完了させること。

## クローラー優先順位制御原則（Smallest-Site-First）
- 物件件数の多い大手ポータル（Homes, Athome）や大手不動産（三井, 住友, 東急, 野村）を後回しにし、処理が早く完了する小規模サイト・電鉄系・ハウスメーカー系から優先的にクロールを実行すること。これにより、大容量サイトの遅延によって他サイトのクロールが未実施になる事態を防止する。

## 連続タイムアウトFast-Fail & サーキットブレイカー原則
- 相手サーバーが無応答・タイムアウトを繰り返す場合（連続3回以上）、ダラダラとリトライを続けず「相手サーバー停止/接続失敗」と判定してジョブを即時中断（Abort）終了し、全体パイプラインのハングアップを防止すること。

## 0件取得のジョブ失敗分類原則
- クローリング処理が正常終了（Exit Code 0）した場合であっても、新規取得件数が0件である場合は「成功」とみなさず「0件取得失敗 (Zero-Count Failure)」としてエラーアラート（Slack/ログ）を発報し、失敗ジョブとして記録すること。


## ML評価の分離 & バルク推論原則 (B案)
- **クローリングとML評価の分離**: クローリング時は同期的ML評価（モデルファイル読込＋推論）を行わず、パースおよびDB保存のみをミリ秒単位で完了させる。
- **バルク推論の実施**: ML 評価はモデルを1回のみメモリロードして一括処理するバルク評価バッチ（`run_bulk_ml_evaluation.py`）または一括評価ステップで処理すること。

## 【普遍開発ルール：SDD（仕様駆動開発）× TDD（テスト駆動開発）統合開発原則】
指示や新規機能要求があった場合、**仕様定義/ドキュメント ➔ テスト ➔ コード実装** の一貫したトップダウンライフサイクルを絶対遵守すること：

1. **Step 1: ドキュメント階層のトップダウン更新 (SDD/DDD)**:
   - 要件定義 (`docs/requirements/`) ➔ 外部設計 (`docs/external_design/`, `docs/basic_design/`) ➔ 内部設計 (`docs/internal_design/`) の順で、コードを触る前に仕様ドキュメントを先行更新する。
2. **Step 2: ドキュメント仕様に基づくテストコード作成 (TDD)**:
   - 更新されたドキュメントの仕様を満たしているかを検証するテストコード（`pytest` 等）をコード実装前にあらかじめ作成・記述する（テストファースト）。
3. **Step 3: ドキュメント ＆ テストに適合する最小コード実装 (Implementation)**:
   - 単一の正（Single Source of Truth）であるドキュメントとテストに従い、テストを通過させる必要最小限（Micro-Diff）のコードを実装する。
4. **Step 4: 先行実装発生時の即用レスキュー補正 (Safety-Net)**:
   - デバッグや緊急修復で実装が先行した場合も放置せず、**可及的速やかに「テストコード化 (TDD) ➔ ドキュメント階層同期 (SDD)」を逆引き補正**する。
5. **Step 5: spec-driven-development (仕様・ドキュメント同期) の必須呼び出し義務**:
   - コード実装や修復作業の最後には、必ず `/spec-driven-development` スキルを実行し、`docs/` 配下の仕様書および [README.md](file:///README.md) の「ドキュメント一覧」が漏れなく同期更新されたことを裏付けること。





## 【プロジェクト普遍ルール】コード修正後の必須テスト実行 & 成功検証原則
- **コード修正後のテスト義務化**: パース修正、バッチ修正、リファクタリング、設定変更などのいかなるコード修正を行った場合も、修正後に必ずテスト（`pytest` または対象モジュールの動作検証テスト）を実行し、エラーが解消して完全に成功することを確認しなければならない。
- **テスト成功までのイテレーション強制**: テストが失敗した場合は、成功するまで修正とテスト実行を繰り返し反復すること。テスト成功の客観的事実を得る前に作業完了を宣言してはならない。
- **物件公開終了 (404/掲載終了) の Slack アラート除外原則**: 物件の公開終了（HTTP 404, Page Not Found, 掲載終了）による取得失敗は正常なライフサイクルであるため、Slack アラートチャンネルへのエラー通知対象から除外（スキップ）すること。


## 【普遍ワークフロー構造：Auto-Heal ＆ Regression-Test 分離原則】
あらゆる不具合修正およびコード変更は、以下の役割分離された2大ワークフロー構造に従って運用すること：

1. **`/auto-heal` （自律バグ修復ワークフロー）**:
   - **役割**: アラート調査および特定箇所の修復作業に特化。
   - **手順**: 把握した問題・アラート一覧をまず整理して最初（Step 1）に Slack へ報告 ➔ 実在する全アラート系Slackチャンネル（`#alerts-mansion`, `#alerts-kodate`, `#alerts-tochi`, `#alerts-invest`, `#alerts-invest-apartment`, `#alerts-invest-kodate`, `#property_alert`, `#dev-agent`）の投稿・スレッドをチェック ➔ 0件取得サイトやパースエラーページの原因特定 ➔ コード/セレクター/ルートの修正 ➔ 修正完了後に `/regression-test` を呼び出して一貫検証。



2. **`/regression-test` （共通品質・セキュリティ検証ワークフロー）**:
   - **役割**: いかなるコード変更後も呼び出される共通リグレッションテスト＆品質保証。
   - **手順**: 
     - **Snyk & SonarQube 全コード走査**: セキュリティ脆弱性・型・静的解析エラーの全件修正。
     - **動的生HTML＆二段階件数検証**: ローカル固定モックに依存せず、最新公開中のアクティブ生HTMLを直接取得。全サイト×種別で先頭3件スモーク ➔ 追加17件（計20件/サイト×種別）へ拡張検証。
     - **純処理時間アサーション**: 静的 1,000ms（1秒）以内/件、Playwright 5,000ms（5秒）以内/件を超過した場合はパフォーマンス劣化バグとしてFAIL判定。
     - **全テスト実行 (pytest)**: `docker compose exec -T app pytest src/crawler/tests/` を全件実行し、単体テストおよびライブ到達・全フィールド動的統合テスト（`test_live_reachability.py`）で 100% SUCCESS を客観的事実として裏付け。

     - **Slack テスト結果自動報告 ＆ 自己検証**: テスト結果の最終サマリー（件数、成功判定、対応ログ）を Slack チャンネルに投稿し、表示結果を自ら確認・自己チェックすること。




1. **TDD（テスト駆動開発）の徹底**:
   - **既存コードに手を加えるとき**: 該当箇所の既存動作を保証するためのテストコードをあらかじめ記載・確認した上で修正を行う。
   - **新しい動き（機能・ロジック）を作成するとき**: 期待している動作が実現できていることを確認するためのテストコードを記載してから実装を行う。

2. **動的アクティブ物件検証（固定モック依存の排除）**:
   - ローカルの古くなった固定モックファイルには依存せず、検証実行時に動的に「現在公開中の最新アクティブ物件生HTML」を直接取得してその場で検証すること。
3. **動的二段階件数制御（3件 ➔ 追加17件＝計20件/サイト×種別）**:
   - 全サイト×全種別に対し、まず**先頭3件**でスモーク検証（Phase 1）を実行し、問題なければ**追加17件（合計20件/サイト×種別）**へ自動拡張（Phase 2）して深い網羅性を検証すること。
4. **純処理時間アサーション（方式別閾値の適用）**:
   - ネットワークHTTP通信待ち時間を除外した「純粋なDOM/パース・処理時間」を計測し、以下のパーサー方式別の現実的な閾値を超過した場合はパフォーマンス劣化バグとしてテスト失敗 (FAIL) とする：
     - **静的HTMLパーサー（三井・住友・東急・野村・ミサワ等）**: **1,000ms（1.0秒）以内/件**


## 【プロジェクト普遍ルール】Slack経由の状況監視・長領域タスク進捗随時リアルタイム報告原則
- **Slack経由依頼での進捗随時リアルタイム報告義務**: Slackから開発指示、状況監視、バッチ実行、長領域の調査・デバッグ等を依頼された場合は、最終結果の一括報告に留めず、進捗が発生する都度（小刻みに）リアルタイムで途中経過・状態変化を Slack スレッドに返信・更新報告しなければならない。


## 【プロジェクト普遍ルール】Slack 返信内容・表示結果の自己チェック原則
- **返信内容・形式の自己検証義務**: Slack へメッセージ投稿や返信を行った後は、どのように返信されたか（メッセージフォーマット、スレッド構造、可読性、エラーの有無）を必ず自ら API やログで取得・確認し、正常に意図通りの表示が行われていることを客観的事実としてチェック・裏付けなければならない。


## 【プロジェクト普遍ルール】ブランチ運用および二段階マージゲートウェイルール (Branching & Merge Rules)
- **ブランチの役割定義**:
  - `production`: 本番環境（GCP Cloud Run 等のデプロイ対象）。直接のコードプッシュおよび作業ブランチからの直接 PR は厳禁。
  - `master`: 統合・検証ブランチ（開発の主幹）。すべての機能追加・バグ修正はまず `master` に集約される。
  - `fix/<topic>` または `feature/<topic>`: 作業ブランチ。すべての開発・修正作業は `master` から分岐した作業ブランチで実施する。
- **マージゲートウェイ原則（Production PR Gate）**:
  - `production` ブランチへの Pull Request は **`master` ブランチからのみ** 許可されている（`.github/workflows/production-gate.yml` により自動検証。他ブランチからの直接 PR は即時クローズされる）。
- **完全二段階マージパイプライン (Two-Stage Release Flow)**:
  1. **Step 1 (作業ブランチ ➔ `master`)**:
     - 作業ブランチをリモートにプッシュ: `git push -u origin <branch-name>`
     - `master` 宛てに PR 作成: `gh pr create --base master --head <branch-name> --title "..." --body "..."`
     - CI チェック通過後、`master` にマージ。
  2. **Step 2 (`master` ➔ `production`)**:
     - ローカルの `master` を最新化: `git checkout master && git pull origin master`
     - `production` 宛てにリリース PR を作成: `gh pr create --base production --head master --title "release: ..." --body "..."`
     - CI（Production Gate & Terraform Plan）確認後、`production` にマージ。マージ完了により本番デプロイパイプライン（`deploy-production.yml`）が自動起動する。

## 【プロジェクト普遍ルール】複数セッション並行開発時の Git ワークツリー運用原則 (Git Worktree Isolation)
- **並行セッションの衝突防止**: 複数のAIエージェントやセッションが同時に稼働する際、同一ワーキングツリー内でのファイル変更・Gitインデックスのバッティングを防ぐため、必ず `git worktree` を用いて独立したワークツリーディレクトリ（例: `../realestate_crawler_<topic>`）を作成して作業すること。
- **ブランチの独立性**: 各ワークツリーは `master` から分岐した専用の作業ブランチ（`feature/<topic>` または `fix/<topic>`）に紐付け、作業完了後は通常フローに従って PR 作成・マージ後にワークツリーを安全に削除（`git worktree remove`）すること。

## 【プロジェクト普遍ルール】PR作成前のローカル静的解析義務化ルール (Snyk & SonarLint Pre-PR Check)
- **事前走査の義務化**: コード修正や新機能追加の後、GitHub に Pull Request を作成・プッシュする前に、必ずローカル環境で Snyk によるセキュリティ脆弱性スキャンおよび SonarLint / SonarQube による静的コード解析を実施すること。
- **指摘事項の解消**: 検出された重大な脆弱性（High/Critical）、Code Smell、型エラー、未解決の指摘はすべて修正してからコミット・PR作成を行うこと。

## 【プロジェクト普遍ルール】パーサー未整備サイトの自律検知およびパーサー新規作成義務化原則 (Parser Missing Detection & Backlog Creation Rule)
- **パーサー未整備エラーの自動捕捉**:
  - クローラーまたは価格推定API (`/api/evaluation/predict-by-url`) において、パーサー未整備エラー（`[PARSER_UNAVAILABLE]` または `[PARSER_NOT_FOUND]`）が発生・ログ出力されたサイトは、一時的エラーや無視できる障害として放置してはならない。
  - これらのエラーは「新規パーサー開発対象（Backlog）の自動検出」として認識し、`CandidatePropertyUrl` テーブルに蓄積されたリクエスト回数 (`request_count`) や重要度に応じて、当該サイト（および物件種別）のパーサー新規実装タスクを自律的に立案・作成しなければならない。
- **パーサー開発・拡張時の必須遵守事項**:
  - 新規パーサーを作成する際は、必ず「物件種別別 Base パーサー階層アーキテクチャ原則」（`MansionParserBase`, `KodateParserBase`, `TochiParserBase`, `InvestmentParserBase` 等の継承と全抽象メソッド実装）および SDD × TDD 統合開発原則（仕様更新 ➔ 単体テスト ➔ 実装）に厳格に従うこと。
  - ルーティング定義 (`UrlRouter`) に正規表現パターンおよび対応パーサー・モデルクラスを追加し、二段階回帰テスト (`/regression-test`) を実行して全件合格を裏付けること。

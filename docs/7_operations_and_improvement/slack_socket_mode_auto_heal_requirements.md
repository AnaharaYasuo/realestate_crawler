# Slack Socket Mode 中継による Antigravity 自律修復トリガー機構 要件定義書

## 1. 概要・ユーザーストーリー
* **ユーザーとして**: 不動産クローラー運用の開発者・保守管理者として
* **要求**: クラウド側（または日次バッチ）でのクローリング異常やデータ不整合の検知時に、Slack Socket Mode 経由でローカルマシンの Antigravity エージェント（`agy.exe`）を自律起動し、自動修復・テスト・PR作成まで完結する中継機構を利用したい
* **価値**: 手動でログを監視してコマンドを叩くことなく、クラウド上のクローラー異常検知からローカル Antigravity による自律修復（Auto-Healing）をリアルタイムに自動実行し、運用の信頼性と復旧速度を最大化する

## 2. 背景と課題
1. **クラウドとローカル間の通信障壁**:
   - クラウド環境（GCP / Cloud Run / VM）からローカル開発機へ直接 Webhook を送信するには、ローカル側にパブリックIPやポート開放が必要となり、セキュリティおよびネットワーク構成上のハードルが高い。
   - Slack Socket Mode は外向き WebSocket 接続を利用するため、ポート開放不要でクラウドからの通知を安全にローカルで受信可能である。
2. **Bot メッセージの無限ループ防止ガードによる阻害**:
   - `slack_agent_host.js` および `slack_agent.py` では、エージェント自身の返信による無限ループ・暴走を防ぐため、`event.bot_id` が付与された全メッセージを無条件で破棄（スキップ）していた。
   - このため、クローラー（パイプラインやスクリプト）が Slack API 経由で Bot としてエラー通知や修復指示を投稿しても、ローカルデーモンが検知できず自己修復がキックされない。

## 3. 機能要件 (Functional Requirements)
* **FR-001: 自律修復トリガー通知発報 (`[AUTO_HEAL_REQ]`)**
  - 全体クローリング完了時（`run_all_crawlers.py` 末尾）または手動 `/auto-heal` 呼び出し時において、異常・データ不整合が検知され指示書（`auto_heal_instruction.json`）が生成された際、Slack の `#dev-agent` チャンネル宛てに特定トリガータグ（`[AUTO_HEAL_REQ]`）を含んだ修復要求メッセージを発報すること。
  - 物件ごとのクローリング中・パース中には集計・AI要約・Slack通知を一切実行しないこと（都度実行の完全禁止）。
* **FR-002: 自動修復トリガーメッセージの選択的認可と自己ループ防止**
  - 常駐デーモン `slack_agent_host.js` および `SlackAgent` (`slack_agent.py`) は、`event.bot_id` が存在する場合でも、メッセージ本文に `[AUTO_HEAL_REQ]` が含まれる場合は自動修復リクエストとして受信を認可すること。
  - ただし、エージェント自身の出力メッセージ（「起動中」「実行中」「タスク完了」等）に対しては厳格に自己ループ防止を適用し、無限再帰起動を確実に遮断すること。
* **FR-003: 一般 Bot メッセージおよび不正ユーザーの確実な遮断**
  - `[AUTO_HEAL_REQ]` タグを含まない通常の Bot メッセージは、従来通り無条件でスキップすること。
  - 人間ユーザーからの通常メッセージについては、引き続き `SLACK_ALLOWED_USERS` に基づく認可チェックを強制すること。
* **FR-004: Antigravity CLI (`agy.exe`) の自律起動と完了報告**
  - トリガー受信後、ローカルの Antigravity CLI をヘッドレス起動し、`/auto-heal` スキルに基づく自律修復を実行し、実行結果を Slack スレッドに返信すること。
* **FR-005: エラー頻度順（Top-50）集計・優先特定および一括実行契機制限**
  - `auto_heal_parsers.py`（またはエラー集計機構）において、パース異常・データ不整合の候補を発生件数が多い順にソートし、上位最大50件（Top 50）に絞り込んで自己修復指示書（`auto_heal_instruction.json`）を生成すること。
  - 実行契機は「全クローラー完了後の一括評価時」または「`/auto-heal` コマンド受領時」の1回のみとし、クローリングループ中の常時実行・逐次呼び出しを禁止すること。
* **FR-006: ログ探索のエラーレベル以上（ERROR / CRITICAL）限定検索**
  - コンテナログの無差別な300行全体読み込みを廃止し、`ERROR` または `CRITICAL` レベルに限定した文字列検索・抽出のみを行うこと。
  - Slack 全チャンネル（8箇所）の巡回探索を廃止し、トリガー情報および指示書を単一の真実（SSOT）としてピンポイントに対象パーサーを特定すること。
* **FR-007: 自己修復完了報告プロトコル（必須報告事項）**
  - 自己修復およびテスト検証の完了時には、必ず以下の3項目を明示・報告すること：
    1. **問題事象**: 発生していたエラー内容、影響を受けた対象サイト・物件種別・URL・エラー件数および根本原因。
    2. **修正内容**: 修正したファイル（パーサー、セレクター、正規表現、設定ファイル等）のパスおよび具体的な変更差分。
    3. **修正後の動作確認結果**: 実施したテスト（`pytest`、`task test-live`、動的取得検証など）のコマンドおよび全件成功（Pass）の客観的事実・証跡。

## 4. 非機能要件 (Non-Functional Requirements)
* **NFR-001: セキュリティ・暴走防止の担保**
  - 不正な外部投稿による任意コード実行を防ぐため、トリガータグは厳格に判定し、エージェント自身の発言との区別を確実に保持すること。
* **NFR-002: 疎結合性・耐障害性・GCS証跡ブリッジ (Issue #1410)**
  - Slack API の一時的な瞬断や未接続時であっても、指示書ファイル（`Temp/auto_heal_instruction.json`）およびクラウドストレージ（GCS `auto_heal/latest_instruction.json` + 日次履歴）への永続化処理自体はエラーで失敗させず、Slack 通知失敗はワーニングとして安全にハンドリングすること。
  - クラウド（Cloud Run）で生成された修復指示書をローカルまたはCI上のエージェントが `--pull-from-gcs` で直接取得でき、DBトンネル未接続時でも自己修復を開始できること。
* **NFR-003: メインエージェント直接実行規約（サブエージェント使用禁止）**
  - グローバルルール（サブエージェント使用の絶対禁止）に準拠し、調査・実装・検証はすべてメインエージェント自身が直接実行すること。コンテキスト圧縮には Gemini 要約済み指示書（`auto_heal_instruction.json`）および `ErrorPageReplayer` を活用する。
* **NFR-004: 全登録サイト網羅 ＆ 閉ループ自動治癒 (Closed-Loop Self-Healing, Issue #1410)**
  - `SiteRegistry` を通じて全登録サイト・全物件種別（`invest_kodate` エイリアスや初回パース例外 `property_id=0` レコードを含む）を漏れなく検証・指示書抽出対象とすること。
  - 異常検知からパーサー修正デプロイ後の再クローリング（`recrawl_anomalies.py` 自動実行＋差分クロール新SHAバイパス）、ML再推論（`recrawled_pending_ml` ➔ `healthy`）、およびお宝物件通知候補への復帰（`is_slack_notified` 非汚染）までが人手介入なしで自律完結すること。
* **NFR-005: GitHub Issue ドリブン × Antigravity Scheduled Automation 自律パーサー修復 (Issue #1412)**
  - ローカル常駐デーモン（`slack_agent_host.js`）への単一障害点依存を解消し、GitHub Issue（`auto-heal` ラベル）を修復キューの単一真実（SSOT）とすること。
  - 日次パイプライン（05:10 JST）完了後、GitHub Actions（`sync-auto-heal-issues.yml`, 毎日 06:15 JST）が GCP OIDC 連携＋`GITHUB_TOKEN` のみ（AIトークン消費ゼロ）で GCS `auto_heal/latest_instruction.json` を読み取り、`(company, property_type)` 単位で重複排除された `auto-heal` Issue を自動起票・最新化・解決時自動クローズすること。
  - 異常が0件となった日次実行時には `auto_heal/latest_instruction.json` をゼロ件状態で上書き更新し、過去の異常指示書の再発火（Stale Replay）および `source_data_invalid`（掲載元データ不備）起因の誤起票を防止すること。
  - パーサーコード修正は個人の **Antigravity 定額トークン枠（Scheduled Automation: 毎日 07:00 JST）** に割り当て、`sync_auto_heal_issues.py --list-actionable` が0件の日は即時終了（トークン消費極小化）、対象ありの日は独立 Worktree 上で SDD/TDD/Parser 修正・検証・PR作成・Auto-merge 設定まで自律完遂すること。
  - 同一 Issue に対する自動修復試行が上限（既定2回）を超過または自動解決不能と判定された場合は、`auto-heal` ラベルを外して `auto-heal:needs-human` ラベルへ昇格させるサーキットブレーカーにより無限リトライを遮断すること。

## 5. アクセプタンスクライテリア (受入基準)
* [ ] 【基準1】`auto_heal_parsers.py` で自己修復指示書が生成された際、Slack の `#dev-agent` 宛てに `[AUTO_HEAL_REQ]` タグ付き自律修復トリガーメッセージを発報できること。
* [ ] 【基準2】常駐デーモン `slack_agent_host.js` および `SlackAgent` (`slack_agent.py`) が `[AUTO_HEAL_REQ]` タグ付きメッセージを受信した際、Bot 発信メッセージであっても安全に無限ループを回避しつつ Antigravity CLI (`agy.exe`) を自律起動できること。
* [ ] 【基準3】パース異常・データ不整合の候補が発生頻度の高い順にソートされ、上位最大50件（Top 50）に優先順位付けされて指示書に記録されること。
* [ ] 【基準4】300行ログの無差別探索および全8チャンネルのSlack巡回が廃止され、ログ探索は ERROR / CRITICAL レベル以上に限定して抽出されること。
* [ ] 【基準5】調査・修復時のサブエージェントは1台のみ稼働とし、安価なモデル（flash/flash_lite等）を用いてコンテキストを圧縮しながら読み込む運用規約が策定されていること。
* [ ] 【基準6】単体テスト (`test_auto_heal_parsers.py`, `test_slack_agent.py` 等) でエラー集計・Top 50抽出およびトリガー判定が検証され、100%成功すること。
* [ ] 【基準7】自己修復完了時に「問題事象」「修正内容」「修正後の動作確認結果」を報告するプロトコルが策定され、スキルおよびドキュメントに明記されていること。
* [ ] 【基準8】SDD ドキュメント（要件定義・基本設計・内部設計・README.md）が同期更新されていること。

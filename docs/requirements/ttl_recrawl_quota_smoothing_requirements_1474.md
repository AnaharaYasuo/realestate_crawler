# 要件定義書: Issue #1474 TTL再クロールの日次クォータ平滑化および社別均等配分

## 1. 背景と課題
14日TTL（Detail Freshness TTL）を経過した掲載中物件（現在約11.7万件）を一括で再クロールすると、以下の重大な課題が発生する：
1. **14日後の再スパイク発生**: 一度に全件更新すると、14日後に再び同規模（11万件超）の更新対象が一斉に出現し、クロール負荷や運用負荷が周期的に跳ね上がる。
2. **社別負荷の偏り**: 抽出件数の多い会社（mitsui 3.2万件、tokyu 2.3万件、homes 2.3万件など）にリクエストが集中し、他社の掲載終了検知や価格更新が後回しになる。

## 2. 目的
1日あたりに更新する件数を均等に制限（日次クォータ）し、かつ各社のTTL経過件数に応じた均等配分（社別クォータ）を行うことで、毎日一定数の物件が安定して更新・循環する運用体制を実現する。

## 3. 機能要件
- **FR-1 (日次全体上限)**: `--daily-quota`（または `--limit`）により、1回の実行（1日）でクロール・更新する最大件数を指定できること。
- **FR-2 (社別均等配分)**: `--company-ratio-quota`（例: `14` 日分割 = 各社のTTL経過対象の `1/14`）または `--company-quota` により、各社ごとの最大処理件数を上限値としてクォータ配分できること。
- **FR-3 (社別クォータの自動算出)**: 各社のTTL経過件数に対して `max(1, ceil(count / ratio))` を社別上限とし、少件数の社（1〜10件）も取りこぼさず、多件数の社（数万件）を均等に抑えること。
- **FR-4 (ラウンドロビン抽出との整合)**: 会社別クォータで制限された対象リストに対しても、既存の `interleave_targets_by_company` によるドメイン分散ラウンドロビン順序が維持されること。
- **FR-5 (CLI オプションおよび既存互換性)**: `--daily-quota`、`--company-ratio-quota`、`--company-quota` の各引数をサポートし、明示指定がない場合は従来の挙動を維持しつつ後方互換性を担保すること。
- **FR-6 (スキップ対象のTTL再取得からの除外)**: 読み取り不可（`transient_skipped`）となった物件、およびパーサー不備（`needs_parser_fix=True` / `needs_recrawl=True`）として別枠管理されている物件は、通常のTTL定期再クロール対象から除外すること。これによりプロセス再起動時や次回実行時に同一の読み取り不可物件が無限に再走するのを防止する。

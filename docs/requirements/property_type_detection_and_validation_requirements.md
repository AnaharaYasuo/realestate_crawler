# 仕様書: PropertyTypeDetector 誤判定防止およびデータ整合性検証最適化要件

## 1. 背景・課題
- **課題1: データ検証（validate_data.py）によるアラート爆発**
  - `scripts/maintenance/validate_data.py` は、全物件種別モデルの `objects.all()` を実行し、全期間（過去数年分の数万件）のレコードを都度スキャンしていた。
  - そのため、過去の古いデータフォーマットや修正前の未クレンジングデータ（`price=0` や面積未取得等）に起因して、毎回 Slack チャンネルに数万件規模の異常アラート（`Critical`）が発報され、真のアクティブな異常の検知が阻害されていた。
- **課題2: PropertyTypeDetector による誤ルーティング（Misclassification）**
  - `PropertyTypeDetector._detect_rule_based` において、`html_text` 内のキーワード判定が `url` 判定より優先されていた。
  - また、`TOCHI_KEYWORDS` に単独の「土地」が含まれていたため、三井のリハウスなどのマンションページ（URL が `/buy/mansion/`）において、フッターや物件概要の「土地権利」「土地面積」等の文言に「土地」が誤ヒットし、種別が `tochi` と誤判定されるケースが発生していた。
  - この結果、`MitsuiTochiParser` 等の誤ったパーサーで詳細ページがパースされ、専有面積が抽出されず `tochiMenseki: 0.000` となり面積異常が記録される不整合を誘発していた。

## 2. 要件一覧
- **REQ-584-01: validate_data の直近アクティブ走査化**
  - `validate_data.py` のスキャン対象を、直近（デフォルト7日間、環境変数 `VALIDATE_DATA_DAYS` で調整可能）に登録・更新されたアクティブな物件レコードに限定する。
  - これにより、恒常的な過去データの重複アラートを根絶し、直近クローリングの真の品質異常のみをリアルタイム検知する。
- **REQ-584-02: PropertyTypeDetector の種別判定優先度最適化**
  - URL に明示的な種別パス（例: `/buy/mansion/`, `/buy/kodate/`, `/buy/tochi/`, `/mansion/`, `/kodate/`, `/tochi/` 等）が含まれる場合は、全文テキストの曖昧なキーワードよりも URL パス判定を優先する。
  - `TOCHI_KEYWORDS` における単独語「土地」による誤検出を防ぎ、文脈（「土地権利」などの一般単語は除外）または売地キーワード（「売地」「売土地」「売り土地」等）を的確に評価する。
- **REQ-584-03: レガシー・不整合データのクレンジング**
  - 過去の誤ルーティングで登録された不整合データ（例: マンションURLであるにもかかわらず `tochi` テーブルに登録されているレコードや、`price=0` の孤立レコード）を安全に修復・整理する。

## 3. 投資用サブ種別判定・居住用賃貸競合防止・土地キーワードクレンジング要件（Issue #623）
- **REQ-623-01: TOCHI_KEYWORDS からの単体語「土地」完全排除**
  - `TOCHI_KEYWORDS` を `["売土地", "売り土地", "建築条件付土地", "売地"]` に限定し、単体語「土地」を完全排除する。
  - 本文中の「土地権利」「借地権」「土地面積」等の文脈が誤って `tochi` 判定される潜在リスクを根絶する。
- **REQ-623-02: 居住用URLに対する本文賃貸シグナル誤判定（オーバーライド）の防止**
  - URL パスに居住用種別（`/mansion/`, `/kodate/`, `/house/`, `/tochi/` など）が明示されている場合、本文中に単に「オーナーチェンジ」「賃貸中」等の表記が含まれていても、居住用ルーティングを優先する。
  - スペック表に明確な数値利回り（`grossYield`）が存在しない限り、本文のテキストマッチのみで投資用（`apartment`）に誤ルーティングされる競合を防止する。
- **REQ-623-03: 投資用サブ種別（一棟アパート・一棟マンション・投資用戸建・ビル等）の識別強化**
  - `PropertyTypeDetector.detect_investment_type` において、「戸建て」「テラスハウス」「戸建」を含む場合は `Kodate`、「マンション」「レジ」を含む場合は `Mansion`、「ビル」「店舗」「事務所」を含む場合は `Building`、それ以外は `Apartment` を返却するよう細分化する。
  - スペック表（専有面積の有無、建物面積、構造等）を考慮した投資用サブ種別判定をサポートし、一律 `apartment` への吸収を防ぐ。

## 4. オートヒール異常解消・低価格物件許容・投資パーサー是正要件（Issue #769）
- **REQ-769-01: 低価格（10万〜100万円未満）および低単価の過剰検知防止**
  - 地目（`chimoku`）が「山林」「原野」「雑種地」「農地」「畑」「田」「保安林」等の場合、または物件名・備考に「山林」「原野」「資材置場」「持分」「オーナーチェンジ」が含まれる場合、あるいは種別が土地（`tochi`）や投資用（`investment` 等）である場合、下限価格チェックを従来の100万円から1万円に緩和する。
  - 平米単価下限についても、山林・原野等の低価格許容物件に対しては従来の1,000円/㎡から10円/㎡まで許容し、正当な安価物件に対する `needs_parser_fix` の過剰検知を防止する。
- **REQ-769-02: 東急リバブル投資用パーサーにおける利回り未抽出の適正化**
  - 利回りが記載されていない投資物件において、`_parseGrossYield` が `Decimal(0)` ではなく `None` を返却するように修正し、バリデータ側で `0%以下` の偽陽性異常判定を誘発しないようにする。
- **REQ-769-03: 東急リバブル戸建て投資パーサーの区分所有物件混入ガード**
  - `TokyuInvestmentKodateParser` において、区分マンション等で土地面積が存在しない物件が混入した場合に `SkipPropertyException` を送出し、不整合な `tochiMenseki=0` レコードの生成を防止する。
## 5. Auto-Heal 単価上限引上げ・面積抽出フォールバック・残留不整合レコード同期要件（Issue #922）
- **REQ-922-01: 都心高額物件の単価上限引上げ**
  - 都心部（港区・千代田区・中央区等）の超高額土地・商業地において、正常な取引であっても平米単価が1,500万円/㎡を超えるケース（例: 虎ノ門土地31.5億円・単価約2,448万円/㎡）が存在する。
  - 上限価格チェックが50億円（500,000万円）まで許容されている整合性を保ち、平米単価の上限閾値を従来の15,000,000円/㎡から50,000,000円/㎡（5,000万円/㎡）へ引き上げ、偽陽性の単価異常検知を防止する。
- **REQ-922-02: 面積抽出における有効候補（>5㎡）へのフォールバック**
  - 投資用アパート等において、業者の登録ミス・ダミー入力により建物面積が極小（例: 1.00㎡）かつ土地面積が正常（例: 91.77㎡）な物件が存在する。
  - `PropertyDataValidator._extract_and_validate_area` において、先頭の面積候補が極小（<=5.0㎡）であっても即座に採用・異常終了せず、後続の面積候補（土地面積等）に有効な数値（>5.0㎡）があればそちらを採用するフォールバック処理を導入する。
- **REQ-922-03: 残留不整合 PropertyEvaluation レコードの同期・正常化**
  - バリデータ仕様更新（モデル定義未存在フィールドのスキップ等）以前に付与されたままの `needs_parser_fix=True` / `data_quality_issue` 残留レコードについて、現行バリデータで合格（valid=True）する場合は自動的にフラグを解消・同期するスクリプトおよび機構を整備する。

## 6. 実行時検知問題の包括的改修要件（Issue #925）
- **REQ-925-01: auto_heal_parsers の project_root パス算出是正**
  - `auto_heal_parsers.py` における `project_root` 算出階層を補正し、自己修復指示書がリポジトリルート直下の `Temp/auto_heal_instruction.json` に正しく出力・配置されるようにする。
- **REQ-925-02: 各サイトパーサーの未抽出項目フォールバック強化**
  - 三井のリハウス・住友・東急等において、所在階、間取り、交通、面積の表記揺れ（改行・空白・特殊ラベル）に対する抽出フォールバックを強化し、未抽出異常の発生を最小化する。
- **REQ-925-03: コードベース全体の静的解析品質改善**
  - `UP006` / `UP035`（非推奨型アノテーションの最新構文への置換）、`PIE790`（不要なpassステートメントの削除）、`SIM101`（重複isinstanceの統合）等、コード品質・静的解析の指摘事項を100件以上安全に解消する。

# マルチイベントループ下でのレートリミット例外解消およびウォッチドッグ監視公平化 要件定義書 (Issue #860)

## 1. 概要
2026年10月10日の定期クローリング実行において、28ジョブでパース失敗およびハングタイムアウト（Code: -1 / Code: 1）が発生し、大量の異常ログが記録された。
本改修では、以下の2つの根本原因を解消し、マルチスレッド・マルチイベントループ環境下での安全なレートリミット制御および親プロセスの安定した進捗監視を実現する。

1. **`api.py` における `asyncio.Lock` のイベントループ不一致例外**:
   - 詳細ページ処理（`_handle_local_execution`）はスレッドごとに新規イベントループを生成するアーキテクチャである。
   - クラス変数に保持された `asyncio.Lock` が別スレッドのイベントループから利用され、`RuntimeError: Lock is bound to a different event loop` が送出されてパースが100%失敗した。
2. **`run_all_crawlers.py` における進捗監視ループの更新抜けバグ**:
   - 進捗監視ループ内に不要な `break` が存在したため、並行実行中の後続ジョブ（`totate`, `sumai1`, `daikyo`, `rearie` 等）の最終活動時刻が更新されず、正常動作中にもかかわらず 600 秒経過で誤って SIGKILL（`hung_timeout`）された。

## 2. 目的とスコープ
* **目的**:
  1. 詳細ページ取得時のレートリミッターをスレッドセーフかつ非同期安全に改修し、マルチイベントループでの例外発生を物理的に根絶する。
  2. ウォッチドッグ監視において、全並行ジョブの進捗チェックを公平に行い、正常稼働中ジョブの誤キルを防止する。
* **スコープ**:
  - `src/crawler/package/api/api.py`
  - `src/crawler/scripts/ops/run_all_crawlers.py`
  - `src/crawler/tests/unit/test_api_rate_limiter_860.py`
  - `src/crawler/tests/unit/test_crawler_watchdog_fairness_860.py`

## 3. 要件一覧
* **REQ-860-01**: `api.py` の `_apply_download_delay_if_needed` において、`asyncio.Lock` による排他制御を廃止し、プロセス共通の `threading.Lock` を用いたタイムスロット予約方式（次回アクセス可能時刻の計算・更新）を導入すること。
* **REQ-860-02**: `threading.Lock` の保持時間は次回アクセス可能時刻の算出・更新のミリ秒間のみとし、実際の待機はロック外で非同期に `await asyncio.sleep(wait_sec)` を実行してイベントループをブロックしないこと。
* **REQ-860-03**: `run_all_crawlers.py` のウォッチドッグ監視ループから不要な `break` を除去し、各ジョブに設定されたインターバル（15秒経過）を満たしたすべてのアクティブジョブの進捗（DB件数増分）を公平に検査・更新すること。
* **REQ-860-04**: 既存のローカルクローリング環境に影響を与えないよう、別コンテナ（専用ポート・コンテナ）で動作確認およびテスト検証を行うこと。

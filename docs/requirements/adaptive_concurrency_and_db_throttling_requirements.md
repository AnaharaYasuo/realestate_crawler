# コンテナ内並列度最適化・適応型詳細並列度およびDB過負荷制御 要件定義書 (Issue #795)

## 1. 背景と課題
- **コンテナリソースの余力**: 現在、Cloud Run Job コンテナ（4.0 GiB RAM / 2 vCPU）において、実行中の平均メモリ消費率は約42%（約1.7 GiB）と、半分以上のリソースが未使用のまま待機している。
- **固定並行度による律速**:
  - ジョブ並行度（`run_all_crawlers.py` の `--parallel`）がデフォルト 6 に固定されている。
  - 詳細ページ取得並行度（`CLOUD_DETAIL_CONCURRENCY`）が固定値（デフォルト 5）となっており、ジョブが 1 つしか動いていない時（三井や athome 等の巨大ジョブ単独実行時）でも 5 並列に制限され、処理時間が長引いている。
- **Cloud SQL（MySQL: db-f1-micro）の過負荷耐性**:
  - 並列度を引き上げた際、MySQL 側のコネクション上限（`Too many connections`）、接続断（`MySQL server has gone away`）、またはロック競合（`Lock wait timeout exceeded`）が発生した際に、クローラープロセス全体がクラッシュせず安全に自動減速（スロットリング）する仕組みが必須。

## 2. システム要件

### 2.1 ジョブ並列度の引き上げ (FR-795-1)
- `run_all_crawlers.py` の通常クローラー並列度（`--parallel` / `--standard-parallel`）のデフォルト値を **6 から 9（1.5倍）** に引き上げる。
- Playwright 並列度（`--playwright-parallel`）はメモリ消費特性（ヘッドレスブラウザ）を考慮し、デフォルト 3 を維持（または必要に応じて安全に調整）。

### 2.2 アクティブジョブ連動・動的詳細並列度制御 (FR-795-2)
- 各クローラーサブプロセス（`main.py`）の詳細ページ同時実行セマフォ（`_getPararellLimit()`）は、単一の固定値ではなく、親プロセスまたはシステム環境から動的に決定可能とする。
- **アロケーション基準**:
  - **アクティブジョブ数が少ない場合 (1〜2ジョブ)**: 1 ジョブあたり詳細並列度 **10〜15** を許可（リソース集約・高速化）。
  - **アクティブジョブ数が多い場合 (3〜5ジョブ)**: 1 ジョブあたり詳細並列度 **5〜8**。
  - **多数同時並行時 (6ジョブ以上)**: 1 ジョブあたり詳細並列度 **3〜4**（全体の暴走防止）。
- 環境変数 `DETAIL_CONCURRENCY_PER_ACTIVE_JOB` や動的状態ファイル、または起動時アクティブ枠計算により、ジョブ横断での最大同時リクエスト数を安全域（トータル 30〜45 程度）に制御する。

### 2.3 DB接続過負荷自己適応型スロットリング (FR-795-3)
- クローラー保存処理（`api.py` の `_save_item_with_retry` / `_save_property_and_price_history`）において、以下のデータベース過負荷エラーを検知すること：
  - `OperationalError` かつエラーコードが `1040` (Too many connections), `2006` (Server gone away), `2013` (Lost connection), `1205` (Lock wait timeout)
- エラー検知時の動作（Circuit Breaker / Throttling）:
  1. **即時並列度縮小**: 詳細並列度を安全最小値（1〜2）に強制ダウン。
  2. **指数バックオフ**: 一時的な接続枯渇の解消を待つため、数秒（1〜5秒）待機。
  3. **自動復帰**: 一定期間エラーが発生しなければ徐々に通常並列度へリカバリ。

## 3. 非機能要件 (NFR)
- **NFR-795-1 (安全性)**: メモリ上限 4.0 GiB を超過（OOM）させず、常時 80% 未満（3.2 GiB 未満）を維持すること。
- **NFR-795-2 (後方互換性)**: `CLOUD_DETAIL_CONCURRENCY` が明示的に環境変数で数値指定された場合は、その数値を静的上限として優先尊重すること。

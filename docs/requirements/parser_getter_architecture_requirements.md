# パーサー Getter メソッド化および表示バリエーション吸収 要件定義書

## 1. 背景と課題 (Issue #564)
- **背景**: 不動産クローラーでは全24サイト×4種別のパーサーが存在し、各サイトで詳細ページのレイアウトやテーブル表記（th/td, dt/dd, table-row, アピール文等）が多岐にわたる。
- **課題**:
  1. `_parsePropertyDetailPage` 内に抽出・型変換ロジックが直書きされ、密結合化・コードの複雑性が増大。
  2. 同一サイト・同一種別でも物件ごとの表示揺れ（例: 道路幅員・道路向き・道路区分・階数・総戸数・土地面積等の表記違いや未記載）により、取得漏れや `ValidationError`（`This field cannot be blank.`）が発生。
  3. 各フィールドの抽出処理が各パーサーに分散しており、表記ゆれへの対応やフォールバック処理の再利用性が著しく低い。

## 2. 目的
1. **パーサークラスの疎結合化**: 取得項目ごとに専用の `get_<field_name>` メソッドを作成し、ページ HTML（`BeautifulSoup`）全体を渡して自己完結させる。
2. **サイト側の複雑性吸収**: Getter 内部で「CSS セレクター ➔ スペックテーブル探索 ➔ 汎用 DOM/正規表現 ➔ converter 型変換」の多段フォールバックを完結させ、呼び出し側の複雑性を上昇させない。
3. **`_parsePropertyDetailPage` の純化**: 抽出ロジックを排除し、各 Getter を呼び出してモデルに格納する宣言的マッピングに移行。
4. **モデル許容性の整合**: 土地物件の階数など、物理的・仕様的に存在しない項目についてはモデル上で空欄（`blank=True`, `null=True`）を許容する。

## 3. 機能要件 (FR)
- **FR-001 (Getter シグネチャ標準化)**: 全フィールドに対応する `get_<field_name>(self, response: BeautifulSoup, specs: dict = None) -> Any` を定義する。
- **FR-002 (文字列・数値分離)**: 数値と生文字列を両立する項目は `get_<field_name>_str` と `get_<field_name>` を提供する。
- **FR-003 (多段フォールバック)**:
  - レベル 1: 専用セレクター / クラス
  - レベル 2: スペックテーブル（同義語・候補キー順次探索）
  - レベル 3: 汎用テキスト / 正規表現
  - レベル 4: converter による型変換・クレンジング
- **FR-004 (種別 Base パーサー配備)**:
  - `ParserBase`: 全種別共通 Getter（価格、住所、物件名、最寄り駅、地代、接道、道路情報等）
  - `MansionParserBase`: マンション特有 Getter（専有面積、階数、総戸数、管理費、修繕積立金等）
  - `KodateParserBase`: 戸建特有 Getter（土地面積、建物面積、構造、間取り等）
  - `TochiParserBase`: 土地特有 Getter（土地面積、建ぺい率、容積率、地目等）
  - `InvestmentParserBase`: 投資特有 Getter（利回り、満室年収、現況等）
- **FR-005 (後方互換性保証)**: 既存の `_parseXxx` メソッド（`test_parser_abstract_methods.py` 対象）を維持・委譲接続する。

## 4. 非機能要件 (NFR)
- **NFR-001 (処理性能)**: 抽出時の純処理時間（ネットワーク除外）は 1,000ms/件 以内。`_get_specs` キャッシュを厳格に再利用する。
- **NFR-002 (テスタビリティ)**: 各 Getter がモック HTML または障害生 HTML に対して単体検証可能であること。

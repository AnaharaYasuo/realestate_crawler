# Issue #1046: 中間・エリアページディスパッチのasyncio.Queueワーカープール化要件定義書

## 1. 背景・課題
- 現在、クローラーパイプラインのローカルディスパッチ（`_handle_local_execution`）において、中間ページ（Start / Area ➔ List）は都度新しいOSスレッド（`threading.Thread(target=run_in_new_loop)`）を生成して投げっぱなし（fire-and-forget）で実行している。
- 東急のように市区町村分割が細分化されたサイト（数千ページ）では、短時間に1,400〜2,000本ものOSスレッドが乱立し、GIL競合とコンテキストスイッチ激増により全体のCPU消化効率が壊滅的に低下する。
- 一方、詳細ページ（Detail）はすでに `asyncio.Queue` + 固定ワーカー（並行度上限）でキュー化されており、スレッド数1本で高スループットを維持している。

## 2. 目的
- 中間ページ・エリアページのディスパッチ処理を、詳細ページと同様に `asyncio.Queue` によるキューイングおよび固定ワーカープール（同一ループ/セマフォ制御）に統一する。
- 1,000本を超えるOSスレッド乱立を完全に排除し、単一プロセス内でのGIL競合を解消して東急等のクローリング速度を劇的に向上させる。

## 3. 要件仕様
1. **スレッド無制限生成の撤廃 (REQ-DISPATCH-001)**:
   - ディスパッチ要求時に都度 `threading.Thread` を生成するのを廃止し、ワーカープール（またはキュー経由）で固定並行度内で消化すること。
2. **詳細ページと同等のキューワーカーアーキテクチャ (REQ-DISPATCH-002)**:
   - 中間ページのディスパッチキュー（`_middle_queue` または共通ディスパッチキュー）を整備し、固定ワーカー数（`_get_local_worker_concurrency()` / `CRAWLER_LOCAL_WORKER_CONCURRENCY`、デフォルト10）で順次実行すること。
3. **後方互換性および既存インターフェースの維持 (REQ-DISPATCH-003)**:
   - `_handle_local_execution` を利用する各社（三井・住友・東急・野村・みずほ・大京等）のルーティングおよび同期・非同期の返却値（200/202）に悪影響を与えないこと。
4. **テスト検証 (REQ-DISPATCH-004)**:
   - 大量ディスパッチ発行時にOSスレッド数が乱立せず、設定されたワーカー上限数以内で整然と処理されることを単体テストで保証すること。

# Cloud Workflows によるパイプライン統合オーケストレーション要件定義書

## 1. 概要・背景
現在、不動産クローラーの日次実行は Cloud Scheduler による時刻ベース起動（JST 01:00 クローラー ➔ JST 03:10 MLパイプライン ➔ 毎時 Safety-Net）として個別ジョブでトリガーされている。
これには以下の課題が存在する：
1. **クロール終了時間とのズレ**: クロールが早く終わっても 03:10 まで待機が発生し、逆に遅延した場合は未完了のまま ML が起動する。
2. **タイムアウト設定の乱立と不整合**: 各レイヤー（Cloud Run Job: 7200s, CRAWL_TIMEOUT_SEC: 10800s, Safety-Net: 7800s など）でタイマーが個別定義され、矛盾が存在する。
3. **インフラ停止の不確実性**: コンテナ自身が OOM やハングを起こした場合に ProxySQL の停止処理が阻害される。

これらを解決するため、**Google Cloud Workflows** を司令塔として導入し、インフラ起動・並列クロール・ML学習・バルク推定・割安物件配信・インフラ停止までを直列統合オーケストレーションする。

## 2. 業務要件 / 機能要件

### REQ-WF-001: エンドツーエンドの直列シーケンス実行
Cloud Workflows により、以下のライフサイクルを1本のワークフローとして順次実行する：
1. **Phase 1: インフラ起動**: ProxySQL GCE インスタンスの起動および疎通待機。Slack パイプライン開始通知。
2. **Phase 2: 並列クローリング**: Cloud Run Job（8タスクアレイ）の実行および完了監視。
3. **Phase 3: データ検証 & ML学習**: 完了データに基づくバリデーション・クレンジングおよびモデル再学習。
4. **Phase 4: 価格推定 & 割安物件配信**: 全件バルク価格推定、割安・お宝物件の Slack 配信、精度診断。
5. **Phase 5: インフラ停止 (finally)**: 成功・失敗を問わず、ProxySQL インスタンスを確実に停止し、総合完了レポートを通知。

### REQ-WF-002: タイムアウトの2重ガード集約
乱立するタイマーを廃止し、以下の2つの上限枠に集約する：
1. **クロール処理タイムアウト**: **5時間（18,000秒）**
   - クロールタスクアレイが5時間以内に完了しない場合、未完了タスクを打ち切って後続フェーズへ進むか異常終了。
2. **ワークフロー全体タイムアウト**: **7時間（25,200秒）**
   - クロール＋ML＋配信の全工程に対し、開始から7時間を経過した場合は強制打ち切り。
   - `finally` ブロックにより、ProxySQL は確実に停止される。

### REQ-WF-003: ハング監視とボトムアップ状態連鎖
1. **無進捗（沈黙）監視**:
   - サブセットジョブ（1社×1種別）において、一定時間（5分）通信・パース進捗がない場合はハングと判定し、該当プロセスグループを強制キル（SIGKILL）して次へ進める。
2. **コンテナ自律終了**:
   - 担当サブセットのキューが空になったコンテナは即座に Exit 0 で自律終了する。
3. **外部からの死活監視**:
   - コンテナ自体の親プロセスがハングした場合でも、Cloud Workflows のポーリング監視によりタイムアウト超過タスクを安全にキャンセル・回収する。

### REQ-WF-004: Slack 通知の完全保証
1. 各ワーカーコンテナからのリアルタイム通知（各社取得結果、お宝物件配信、エラー）は従来通り継続。
2. Cloud Workflows から直接、開始通知、終了サマリー通知、異常中断通知を Slack API へ送信。

## 3. 非機能要件
1. **コスト最小化**: クロールが早く終われば即座に ML ➔ 配信 ➔ ProxySQL 停止へと進み、アイドルのインフラ課金をゼロにする。
2. **耐障害性**: いかなる例外・タイムアウト・コンテナクラッシュ時も、Workflows の `try-finally` 機構により ProxySQL インスタンスの停止を 100% 保証する。
